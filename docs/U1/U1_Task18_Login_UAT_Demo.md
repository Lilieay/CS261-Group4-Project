### เกณฑ์การตรวจรับ

- ผู้ใช้ที่มีข้อมูลถูกต้องเข้าสู่ระบบได้ และเห็นข้อความสำเร็จหรือถูกนำไปหน้าถัดไป
- ผู้ใช้ที่กรอกข้อมูลผิดไม่เข้าสู่ระบบ และเห็นข้อความผิดพลาดที่เหมาะสม
- ฟอร์มแจ้งเตือนเมื่อกรอกข้อมูลไม่ครบหรือรูปแบบไม่ถูกต้อง
- เมื่อ Backend ไม่พร้อม หน้าเว็บไม่ค้างและแสดงข้อความผิดพลาดกลางเดียวกับกรณี Login ถูกปฏิเสธ
- ไม่แสดง password หรือรายละเอียดภายในของ TU API ให้ผู้ใช้เห็น
- หลัง Logout token เดิมไม่สามารถเรียกข้อมูลผู้ใช้ปัจจุบันได้

## 2. Demo Script

ส่วนนี้เป็นขั้นตอนเตรียมสาธิต ไม่ใช่ผล Demo จริง

### ก่อนเริ่มสาธิต

1. ตรวจว่าใช้ commit/รุ่นเดียวกับที่ระบุในตาราง UAT
2. ตั้งค่า Backend เป็นโหมด mock สำหรับการสาธิตในเครื่อง หรือเตรียม TU API จริงตาม environment ที่ได้รับอนุญาต
3. เปิด Backend ที่ `http://127.0.0.1:8000`
4. เปิด Frontend ที่ `http://127.0.0.1:5000/login.html`
5. เตรียมข้อมูล `6800000000 / 0000000000000` และ `6800000000 / wrong`
6. เปิด Developer Tools ไว้สำหรับแสดง Request/Response เฉพาะที่จำเป็น โดยไม่แสดง password หรือ token เต็มค่า

### ลำดับการสาธิตหลัก

| ลำดับ | การกระทำของผู้สาธิต | สิ่งที่ต้องเห็น |
|---|---|---|
| 1 | เปิดหน้า Login | เห็นฟอร์มรหัสนักศึกษาและรหัสผ่าน ปุ่ม Login พร้อมใช้งาน |
| 2 | กรอก `6800000000` และ `0000000000000` แล้วกด Login | เกิด `POST /api/auth/login` และระบบแสดงผลสำเร็จ/นำไปหน้าถัดไป |
| 3 | ตรวจสถานะ Login | `GET /api/auth/status` ตอบ `logged_in: true` เมื่อส่ง Bearer token |
| 4 | กลับหน้า Login หรือเปิดใหม่แล้วกรอกรหัสผ่านผิด | ระบบไม่ให้เข้าสู่ระบบและแสดงข้อความผิดพลาดทั่วไป |
| 5 | เว้นข้อมูลบางช่องแล้วกด Login | หน้าเว็บแจ้ง validation โดยไม่ส่ง Request ที่ไม่ครบ |
| 6 | กด Logout หรือเรียก Logout ตาม flow ของระบบ | `POST /api/auth/logout` สำเร็จ และ session ถูกยกเลิก |
| 7 | เรียก `/api/auth/me` ด้วย token เดิม | ได้ `401` และไม่สามารถอ่านข้อมูลผู้ใช้หลัง Logout |

### เรียก Status และ Logout ด้วย token ของหน้าเว็บ

หลัง Login สำเร็จ เปิด Developer Tools Console ของ frontend origin และแท็บเดียวกับที่ Login แล้วรันคำสั่งต่อไปนี้ คำสั่งอ่าน token จาก `sessionStorage` key `access_token` และส่งผ่าน frontend proxy โดยไม่พิมพ์ token ออกมา

```javascript
const token = sessionStorage.getItem('access_token');
if (!token) throw new Error('Login in this tab first');
const headers = { Authorization: `Bearer ${token}` };
const statusResult = await fetch('/api/auth/status', { headers });
console.log('logged_in:', (await statusResult.json()).logged_in); // true
const logoutResult = await fetch('/api/auth/logout', { method: 'POST', headers });
console.log('logout HTTP:', logoutResult.status); // 200
const meAfterLogout = await fetch('/api/auth/me', { headers });
console.log('me after logout HTTP:', meAfterLogout.status); // 401
sessionStorage.removeItem('access_token');
```

ตัวแปร `headers` ยังถือ token เดิมสำหรับตรวจว่าถูกยกเลิกแล้ว ส่วนคำสั่งสุดท้ายลบ token จาก browser ไม่ใช่การยกเลิก session ฝั่ง Backend การยกเลิกเกิดจาก API Logout อย่าบันทึก token หรือรหัสผ่านในหลักฐาน

### สาธิตกรณี Backend ไม่พร้อม

1. หยุด Backend โดยคงหน้า Login ไว้
2. กรอก `6800000000 / 0000000000000` ให้ผ่าน validation แล้วกด Login
3. ตรวจว่ามี request จริงและแสดงข้อความกลาง “เข้าสู่ระบบไม่สำเร็จ กรุณาลองใหม่อีกครั้ง” เช่นเดียวกับกรณีรหัสผ่านผิด
4. ยืนยันว่าหน้าเว็บยังตอบสนองและสามารถลองใหม่หลังเปิด Backend ได้

### ผลที่ต้องเห็นในการ Demo

- Flow สำเร็จและ Flow ผิดพลาดแสดงผลต่างกันอย่างชัดเจน
- API รับข้อมูล Login เป็น JSON และไม่ส่ง password กลับใน Response
- Response สำเร็จมี `access_token`, `token_type` และข้อมูลผู้ใช้ที่เปิดเผยได้
- การตรวจสถานะและ Logout ใช้ Bearer token เดียวกัน
- หลัง Logout token เดิมถูกปฏิเสธ
- หลักฐาน Demo ต้องมาจากการรันจริงของรุ่นระบบที่ระบุ ไม่ใช่จากตัวอย่างในเอกสารนี้
